## これは何の記事か

JPYCを店で受け取れるようにするだけなら、QRを出してウォレットで送金してもらえばよい。でも、実際のレジではそれだけでは足りない。

- 金額が少し足りない。
- 期限後に届く。
- 二重に送られる。
- 返金が必要になる。
- 日次締めで説明できない。
- スタッフが「商品を渡していいのか」を判断できない。

JPYCを受け取れることより、受け取った後に店が困らないことが大事です。

この記事は、JPYC（資金移動業型 ERC-20 ステーブルコイン）を小規模店舗・イベント・ポップアップの現場で扱うために、請求発行から着金検知、過不足対応、返金証跡、日次締めまでを一貫して支える **non-custodial Merchant Ops / Settlement Layer** を設計・実装した記録です。**本リポジトリの初期運用スコープは Polygon です。** JPYC エコシステム自体は別チェーンでの発行・利用も進んでおり「JPYC は X / Y / Z のみ対応」とは書きません。本実装では承認済み運用範囲に従って対象チェーンを Polygon に限定しています。

作ったものを一言で言うと、**スタッフが暗号資産を知らなくても、JPYCの請求・着金確認・過不足対応・返金証跡・日次締めまで回せる、ノンカストディ型の店舗運用OS** です。

現時点では「実JPYC少額決済」「実機ウォレット起動」「公開TLS環境」「店舗スタッフによる訓練」「法務/AML/APPI/会計承認」のいずれも外部検証が完了していないため、本記事の段階は **限定実証前の準備完了** です。これらが揃った時点で初めて実証が始まります。

コードが動くことと、実証が始まることは別のことです。そこを曖昧にしません。

## 作ったものの立ち位置

「JPYC決済機能」を作ったのではなく、**JPYCを受け取ったあとの現場運用を支える基盤**を作りました。

汎用の支払い受付だけなら、いずれ標準的なウォレット、QR、決済代行、加盟店網が強くなります。そこは大手やインフラ事業者が強い領域です。私たちが解こうとしているのは、**支払いが検知されたあとに何が起きるか**という問題です。

- 金額が少し足りない → 確認待ちキューに入れ、スタッフに次の安全な操作を案内する
- 期限後に着金した → 自動でペイドにせず、期限後着金として確認待ちに送る
- 重複送金が疑われる → 全件でブロックし、管理者確認まで引き渡しを止める
- 日次締めに未解決レビューがある → 締めをブロックし、スタッフに明示する
- 返金が発生する → 外部ウォレットで実行されたトランザクションを記録・検証し、二名承認ルールのもとで台帳に反映する

これらは、決済機能ではなく **現場運用OS** の仕事です。小さな店舗やイベントでは、ひとつの例外対応がレジ前の滞留やスタッフの不安につながります。だから「払える」より先に、「支払い後に迷わない」を設計の中心に置きました。

## 非カストディ原則

本システムは顧客の秘密鍵を保持せず、資産を預かりません。

送金は顧客のウォレットアプリが実行します。本システムは EIP-681 形式の送金URIと、ウォレットアプリへのディープリンクを返すだけです。顧客のスマートフォンを預かること、秘密鍵やシードフレーズを聞くことは、設計段階から禁止操作として明文化しています。

この原則は、スタッフ向けの表示語彙と操作ガイドにも反映されています。「払い戻し」「返金する」といった表現を店頭UIから排除し、「外部ウォレットで返金を実行済みであることを確認したうえで記録する」という手順を徹底しています。

## 設計上の主な判断

### Invoice-first ledger

請求（invoice）を先に発行し、それに対して着金を突き合わせる設計です。請求なしの着金は処理しません。ステータスは `issued → payment_detected → confirming → paid` の経路が正常系で、逸脱は `review_required` に送ります。`expired` 後の着金を `paid` にすることは許可していません。

### 確認ブロック数の保守設定

確認ブロック数はリポジトリの confirmation policy 設定に従います。Polygon のチェーン再編成リスクを考慮し、現在の既定は `REQUIRED_CONFIRMATIONS=2` / `MIN_REQUIRED_CONFIRMATIONS=2` です。「1確認で通る」と固定する設計は採用していません。承認済みの docs / env が変わらない限り、この値は変更しません。

### review queue と operator action policy

例外が発生したとき、スタッフに「商品を渡してよいか」「次にすべき操作」「店長確認が必要か」を即座に案内する operator action policy を実装しています。理由コードごとに安全な出口操作を定義し、スタッフが暗号資産の内部状態を知らなくても対応できるようにしています。

### 日次締めと監査ログ

日次締めは `review_required` の未解決レビューがある状態では実行できません（canonical 設定は `SETTLEMENT_UNRESOLVED_REVIEW_POLICY=block`。旧フラグ `SETTLEMENT_BLOCK_ON_UNRESOLVED_REVIEWS=true` は後方互換のためにのみ残しています）。監査ログはハッシュチェーンで整合検証できます。

### 返金の記録・検証

返金はシステムが送金を実行しません。外部ウォレットで実行されたトランザクションのtx hashを登録し、オンチェーンで内容（from/to/amount/confirmations）を検証したうえで台帳に反映します。申請者と承認者の同一性もAPIレベルで拒否します。

## 大手と競争しない理由

大手カード決済サービスや大手QRコード決済は、加盟店数・ユーザー数・ブランド力・不正検知精度のいずれでも勝てません。同じ土俵で戦う理由がありません。

私たちが着目しているのは、**大手が標準化しにくい現場の小さな例外**です。

少額決済、イベント会場、小規模実証、特定コミュニティ向けの受け取り——こういった文脈では、汎用決済の「例外はカスタマーサポートへ」という案内より、「今この請求に何が起きていて、次にスタッフが何をすればよいか」をリアルタイムで案内するほうが実用的です。

現場で止まる問題を、現場で解決できるシステムを作ることが差別化の本質です。
