# Phase 2 成果物: 決済方式ADR（20-payment-method-adr）

## Goal
JPYC店頭決済で採用する実装方式を比較し、推奨案を提示する。

## Context
現状は疑似QRとモック遷移であり、実決済処理が存在しない。

## Constraints
- 法務未承認のまま確定決定しない。
- ここでの結論は `Proposed` とし、正式採用は承認ゲート後。
- 秘密鍵をフロントエンドに置く方式は採用しない。

## 比較対象
- Option A: 店舗固定アドレスへのERC-20送金
- Option B: 請求ごとのユニーク受取アドレス
- Option C: スマートコントラクト請求
- Option D: WalletConnect/Reown AppKit 送金リクエスト中心
- Option E: JPYC社APIまたは外部決済API連携

## 比較表
| 観点 | A 固定アドレス | B ユニークアドレス | C コントラクト | D WC中心 | E 外部API |
|---|---|---|---|---|---|
| 実装難易度 | 低 | 中 | 高 | 中 | 中 |
| 期限制御 | 低 | 中 | 高 | 中 | 高(提供次第) |
| 重複/照合 | 低 | 中 | 高 | 中 | 高 |
| 監査性 | 中 | 高 | 高 | 中 | 高 |
| 返金運用 | 中 | 中 | 中 | 中 | 提供次第 |
| ベンダ依存 | 低 | 低 | 低 | 中 | 高 |
| セキュリティ設計 | 中 | 高 | 高 | 中 | 中〜高 |

## 推奨案（暫定）
`Option B + Option D` のハイブリッドを推奨。

理由:
- 店頭UXとしてWalletConnect導線を実装しやすい。
- 請求ごとの識別性が高く、台帳照合が容易。
- 固定アドレス方式より重複判定と監査が容易。
- コントラクト方式より初期実装を短縮できる。

補足:
- ただし法務上の責任分界、返金主体、対応チェーンは別ゲート承認が必要。

## 非採用（現時点）
- Option Cは将来的候補。MVP本番化初期には設計・監査コストが高い。
- Option A単独は照合・誤送金対応・監査の運用負荷が高い。

## 意思決定ステータス
- Status: Proposed
- Required approvers: 技術責任者、運用責任者、法務責任者

## Done when
- 推奨方式が承認され、`Accepted` に更新される。
- 非採用理由が記録される。

## Validation
- `docs/21-chain-and-token-spec.md` と `docs/22-wallet-support-plan.md` の前提に整合する。

## Failure handling
- 承認前は実決済機能の実装を開始しない。
